## Amendment 1: fail-closed credential-file allowlist (`live_transport.py`)

Replaces deny-list checking. On Windows the file passes only if **all** hold: the current user's SID is read from the process token; the file's **owner** is that SID, SYSTEM or Administrators; the DACL exists, is not NULL and parses completely; every allow-type ACE (`A`, `OA`) names only the current user, SYSTEM (`SY`/`S-1-5-18`), Administrators (`BA`/`S-1-5-32-544`) or OWNER RIGHTS (`OW`/`S-1-3-4`). Deny ACEs are ignored; every other ACE type (conditional, callback, audit), alias, SID, group, service account, AppContainer or unknown token is refused; any failure to read the ACL, owner or current SID refuses. SYSTEM and Administrators are tolerated because they can read or take ownership of any file anyway; OW is safe because the owner must already be on the list. The file is also re-checked after it is read (identity and ACL), so a swap between check and read is refused.

Tests (real files, fake content, `tests/blindplay/test_audit_017_live.py`, `test_live_transport.py`): a real file shared with **another specific user SID** (current user's domain plus RID 503 and 504) is refused and the tests fail rather than skip if the grant fails; real files granted LOCAL SERVICE, NETWORK SERVICE, Backup Operators, Remote Desktop Users and all-services are refused; an Everyone grant on the fixture credential is refused by the **unpatched** gate; NULL DACL, foreign owner, unknown current SID and malformed SDDL are refused; swap-during-read, rewrite-in-place, link-swap and ACL-widened-during-read are refused.

Known limits: group membership is not expanded; SDDL prints the built-in Administrator (RID 500) and Guest (RID 501) accounts as the aliases `LA`/`LG`, so those aliases are accepted only when they are the current user's own account (found by CI: GitHub's Windows runner runs as the built-in Administrator and its own files were refused; fixed with tests); a swap that restores identical file index, size and mtime is not detectable without opening once and using the handle; the tests run on Windows only (CI's macOS and Ubuntu runners skip them); never exercised on a real key.

## Amendment 2: budget-matched baseline request limits (`host.py`, `baselines.py`, `results.py`)

* `host.py` CLI: `--max-requests` (default unchanged, 20,000).
* `baselines.py`: the plan (`react.blindplay.baseline-plan.v2`) has two **labelled** conditions of seven runs: **`matched-1000`** (`--max-requests 1000`, the budget-matched control) and **`diagnostic-20000`** (`--max-requests 20000`, extended scripted diagnostic, **not** budget-matched). `--max-requests` is in every command and in the plan hash (which also covers labels and roles, not the output path). A known label can never carry another limit; custom labels exist for dry-label tests only and are labelled "NOT budget-matched, NOT an official condition"; `only_scripts` is refused on an approved run. `run` still needs `--i-have-owner-approval-reference`, never overwrites and refuses official-looking directories. The default plan hash for `keyset.v2`, 10 episodes, 8,000 frames (14 runs) is printed by `baselines plan --keyset keyset.v2 --out-root <path that does not exist>`; recomputed on `e44d149`: `plan_sha256 bb527a18a5ad88e82769ee800d97b2bfe8c9de73d856be688024e0286d6922dd`.
* `results.py`: a session ended early by the request limit is reported as **`CENSORED_BY_REQUEST_LIMIT`** (planned versus finished episodes, the limit, requests used, the partial episode, from recorded data only, `unavailable` otherwise) and is INCOMPLETE; a condition label that disagrees with the session's recorded limit is `CONFLICT`; the condition is stated only if the run log records it.
* Behaviour of the limit (code, `session.py`): every game request counts (brief, observe, act); past the limit each request is rejected with "request budget exhausted". What happens next depends on the player: **the scripted baseline player exits on the first rejected request** (unplayed episodes leave no record), while **an AI session is ended by the gateway with stop reason `game_request_limit`** (rule 17; Mission 017; `test_the_referees_request_budget_error_ends_the_session_with_no_further_model_call`). The earlier statement that the session "is not otherwise ended" referred to the host/referee only and is superseded by this wording.
* **Correction (Mission 019).** The first version of this document expected key-sweep to be "censored after about 2 episodes" at 1,000 requests, from arithmetic of about 400 `act` requests per episode. That is **wrong**: episodes end on a crash, well before 8,000 frames. One disposable, non-study measurement (`key-sweep`, `keyset.v2`, game seed 0, one episode, host `--max-requests 20000`; not an official baseline) crashed at frame 1,749 after 90 game requests (89 observations) in 6.6 s. If the other episodes behave similarly, a 10-episode key-sweep needs roughly 900 requests, close to but not clearly over 1,000. This is measured on **one episode only**; other episodes and scripts are unmeasured, and censoring will be reported from recorded data. Episode 1 of key-sweep is deterministic (game seed 0, fixed start, step counter from 0), so this disposable episode is expected to be identical to episode 1 of both official key-sweep runs. It was observed before authorization; no setting changed after it, and the frozen plan hash comes from code at `e44d149`, which predates the observation. The scratch data was not kept in the repository. Baseline runs are also not independent samples and are reported per run, never pooled (candidate protocol §9).
* Candidate protocol §9 was updated in Mission 018. `docs/LIVE_TRANSPORT_PREPARATION.md` was updated for the credential check in Mission 018 but had **no** `--max-requests` text until Mission 019, which added a short "Scripted baselines and `--max-requests`" note there.
